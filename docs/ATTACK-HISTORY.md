## 🧬 Часть 1. Как устроена капча

**Поле:** 160×160 px · **~9200 точек** · палитра 6 цветов + тёмный фон `#0e0e18`
**Сетка:** шаг 2 px · **Клетка глифа:** 5 px · **Блок кода:** 23×7 клеток (115×35 px) · **20 fps, 30 секунд**

### Принцип «нулевого знания на кадр»

```
┌───────────────────────── один кадр ─────────────────────────┐
│  ● ●●  ●   ●●●  ●● ●    ← фон: точки, неотличимые от кода  │
│ ●  ●● ●●●●  ● ●●  ● ●●      (плотность, цвета, размеры,    │
│  ●● ●  ● ●●●● ●  ●●●        время жизни — всё выровнено)   │
│ ●  ● ●● ●  ● ●●●  ●  ●                                      │
└──────────────────────────────────────────────────────────────┘
```

| Механика | Что делает | Зачем |
|---|---|---|
| 🎬 Сборка | 1 с код невидим → 1.5 с точки слетаются в блок | жёсткое тело — сигнал для глаза |
| 🫁 «Дыхание» + вращение | перенос ±2.5 px, поворот ±12° | ломает попиксельный трекинг |
| 🧲 Захват точек | дрейфующая точка, попав в клетку, «захватывается» | убирает артефакты рождения/смерти |
| 🔒 Проверка | SHA-256 с солью на сервере, код живёт 30 с | перехват ответа бесполезен |

## ⚔️ Часть 2. Внутренняя разработка решателей (полная хронология)

### 🧪 Эксперимент 1 — `analyze.rs` (блоб-анализ)

**Идея:** найти отдельные точки и сопоставить их между кадрами по цвету и позиции.

**Что получилось:**
- покрытие поля ~0.52, блобов ~850/кадр, из них «чистых» точек ~450;
- лучший сдвиг `d=(0,1)` с совпадением 705‰ — но это размазанный пик, не блок.

**Вывод:** ❌ точки перекрываются (до 4 штук на пиксель), попиксельный трекинг невозможен.

### 🧪 Эксперимент 2 — `flow.rs` (оптический поток)

**Идея:** построить поле скоростей и найти область с согласованным движением.

**Что получилось:** в ASCII-визуализации потока доминирует общий дрейф фона; блок не выделяется.

**Вывод:** ❌ направление фона и текста слишком близки, нужна не потоковая, а «жёсткая» модель.

### 🧪 Эксперимент 3 — `vtest.rs` (оценка смещений по окнам)

**Идея:** для окон 40×40 оценить доминирующее смещение между кадрами.

**Что получилось:** оценка `est=(1,−1)` при истинном `(0.2,−0.4)`; ошибка 0.78–1.82 px.

**Вывод:** ⚠️ направление движения оценивается, но точности для выравнивания не хватает.

### 🧪 Эксперимент 4 — `tsearch.rs` (поиск трансформа) — 💡 прорыв

**Идея:** вычесть из кадров **временное среднее** (оценку фона) и найти прямоугольник 115×35,
который лучше всего объясняет остаток — перебором позиции и угла.

**Что получилось:** ошибка локализации 2.8–11.3 px (в среднем ~4.7 px) — блок находится стабильно.

**Вывод:** ✅ это стало фундаментом финального решателя.

### 🧪 Эксперимент 5 — `track.rs` (трекер с предсказанием)

**Идея:** вести блок от кадра к кадру со сглаживанием скорости и локальным поиском ±3 px.

**Что получилось:** сигнал плотности блока против фона — всего **0.035**; клеточного контраста нет.

**Вывод:** ❌ непрерывный трекинг не нужен: надёжнее независимая локализация каждого кадра + EM.

### 🏆 Финал — `solve2.rs`

```
кадры ──► временное среднее (фон) ──► вычитание ──► matched filter (позиция + угол)
   │                                                      │
   └────────► накопление клеток 23×7 ◄── EM×4: шаблон → ре-выравнивание → веса → отсечка 30%
                        │
                 декод по шрифту 5×7
```

| Этап | Суть |
|---|---|
| 1. Фон | покадровое среднее покрытия после сборки (t ≥ 2.2 с) |
| 2. Локализация | прямоугольный matched filter, грубо (3 px / 2°) → точно (1 px / 0.5°) |
| 3. Сглаживание | медиана по 7 кадрам + интерполяция |
| 4. Накопление | проекция всех кадров в канонические координаты блока |
| 5. EM ×4 | мягкий шаблон → ре-выравнивание → взвешивание по корреляции, худшие 30% в отсечку |
| 6. Декод | контраст «лит−нелит» по каждой из 10 цифр шрифта; уверенность = отрыв от второго |

**Результаты (исходная версия капчи):**

| Набор | Точных | По цифрам |
|---|---|---|
| 6 сэмплов (старый набор) | 5/6 | 87.5% |
| 30 свежих (сид 2024) | 20/30 (66.7%) | 81.7% |
| 30 свежих (сид 2025) | 25/30 (83.3%) | 93.3% |
| **Итого** | **50/66 ≈ 75.8%** | **≈ 87.5%** |

**⚡ Оптимизация:** горячие циклы (локализация, EM, накопление) распараллелены через `std::thread::scope`
без внешних зависимостей: **37 с → 8.5 с на GIF (×4.4)**, 12 потоков.

### 🌊 `solve3.rs` — вариант под flow-режим

Во время эксперимента с flow-режимом (движущаяся форма без статической структуры) был создан `solve3`:
контраст инвертирован — в flow **лит-клетки беднее фона**:

```rust
// flow:  score = us/un − ls/ln      (лит-клетки «худее»)
// classic/jelly: score = ls/ln − us/un
```

**Почему не работал на текущей капче:** 🔍
1. локализация и декод искали «инвертированный» контраст (верно только для flow);
2. старт с 0-го кадра включал фазу сборки (когда блока ещё нет) и портил оценку фона;
3. не учитывал пульсацию масштаба ±25%.

**Исправлено:** аргумент `flow`, старт с 2.2 с, знак контраста по режиму.

## 🌍 Часть 3. Атаки сообщества (защита v8)

> Оба отчёта сделаны против публичного демо на **защите v8** (классическая механика, до пульсации
> масштаба). На текущей **v10** их подходы не проверялись, но все внутренние замеры показывают 0%.

### 🤖 Отчёт Z.ai «Super Z» (30.09.2026)

Четыре итерации CV-солвера:

| # | Подход | Результат |
|---|---|---|
| 1 | FFT-кросс-корреляция кадров | пик (+1,−1), SNR 1.72 — но накопление даёт шум |
| 2 | Motion-compensated accumulation | ~100% ложных срабатываний (плотность 46%) |
| 3 | Multi-frame consistency (K=2…6) | выжило 5779 → 2850 → 1377 → 716 → 401 px, макс. компонента **14 px** |
| 4 | Temporal correlation map | excess: среднее +8.75, макс +50.39, σ=13.29 — равномерный шум |

> «Технология действительно реализует принцип „нулевого знания на кадр“ в строгом смысле»
> — отчёт Z.ai

**Формальный «успех» на демо** был получен через **утечку метаданных**: `samples/labels.csv`
в открытом репозитории → определение текущего GIF на странице → ввод ответа.
Этот путь **запрещён правилами челленджа** и не работает против продакшена
(в .NET-приложении код генерируется динамически и хранится только как солёный хэш).

Их честные метрики по CV: **4/100 точных (4%)**, 36/100 с 3+ цифрами, средняя по цифрам 52%.

## 🧠 Часть 6. Выводы

1. **«Нулевое знание на кадр» — работает.** Ни один попиксельный, попарнокадровый или
   корреляционный метод не выделил цифры: сигнал плотности блока всего ~0.035.
2. **Прорыв возможен только через жёсткую модель + накопление.** Единственный работающий
   подход — временное среднее + matched filter + EM (наш `solve2`).
3. **Пульсация масштаба ломает и это.** После ±25% ни один из четырёх решателей не проходит порог.
4. **Сообщество подтверждает:** лучший честный CV-результат — 4% (порог 50%).
   Единственные «успехи» на демо — утечка `labels.csv`, запрещённая правилами.
5. **Дальше:** устойчивый решатель требует long-horizon трекинга + RANSAC-сегментации
   жёсткого тела + OCR, обученного на сгенерированных данных (оценка: 5–10 дней работы).

## 🔧 Приложение: воспроизведение

```powershell
# сборка
cd generator; cargo build --release

# генерация: <код> <файл> [fps] [секунды] [classic|jelly]

.\target\release\solve.exe  sample.gif            # эталон (0%)
```

